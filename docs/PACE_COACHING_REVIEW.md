# 현재 페이스 보정과 코칭 정책

코너에서 느리게 들리거나 ±5초/km 경보가 잦다는 것은 사용자 실기기 보고이며, 아래 합성 입력의 코드 원인과 현장 원인 확정은 구별한다.

## 코너·곡선 페이스 보정

기존 엔진은 제공자 속도를 이동 여부에만 사용하고, 유효 GPS 좌표 사이의 직선 거리를 누적하여 최근 20초의 운동 시간/거리로 현재 페이스를 계산한다. 샘플 사이에 코너가 있으면 그 직선은 실제 경로보다 짧다. 원호에서는 `chord = 2R sin(vΔt/(2R))`, 실제 이동은 `vΔt`다. 90도 회전의 양쪽 길이가 같은 한 선분은 직선 거리 비율이 `1/√2`다. 이것은 이상화된 일정 속도 기하이며 실제 코너 감속이나 특정 폰의 GPS 원인을 입증하지 않는다.

속도가 없는 위치는 매 선분이 `max(2.5m, accuracy/2)`를 넘어야 이동으로 인정한다. 고밀도 위치에서는 이 절삭도 별도 손실 원인이다. 요청 1초·최소 500ms는 실제 위치 갱신을 보장하지 않는다. 이번에는 정지 잡음/자동 정지에 영향을 주는 거리 필터를 바꾸지 않는다.

`ProviderPaceWindow`는 Android 속도 정확도가 함께 있고 앱의 품질 조건을 통과한 속도의 시간 가중 사다리꼴 적분을 **현재 페이스 추정에만** 사용한다. 연속 관측점의 20초 창과 최소 8초 준비를 유지한다. 기존 좌표 창의 최소 8m 이동 근거도 있어야 제공자 추정을 선택한다. 품질 결측/불량은 제공자 창을 비우고 기존 좌표 값으로 돌아간다. 이후 최소 8초의 유효 속도로 다시 준비한다. 속도 창이 준비됐어도 적분 거리 8m 미만이면 현재값은 없음이다.

속도는 유한 0~12m/s, 불확실성은 유한 0~0.3m/s 및 양의 속도의 10% 이하를 요구한다. 이 숫자는 보수적인 앱 게이트이며 Android의 정확도 보장이나 ±5초/km 정확도 보장이 아니다. 품질이 좋은 것으로 표시된 편향된 속도도 틀릴 수 있다. 0속도는 결측으로 대체하지 않는다. 정확도 불량·점프·수신 만료·표본 간격 15초 초과·정지/재개에 속도 근거를 연결하지 않는다. 창에 중복/역순 시간을 추가하지 않는다.

저장 `TrackPoint`·누적 거리·전체/1km 평균·목표 도달 경계·구간 전환·코스 지점 및 route progress는 기존 계산 그대로다. 제공자 속도로 거리를 기록하거나 경로를 코스에 스냅하지 않는다. 현재와 기록 평균은 다른 근거의 추정값일 수 있다. `providerPaceUsed`는 저장하지 않는 개발 진단이다.

## 공식 API 확인

2026-10-11에 [Android Location](https://developer.android.com/reference/android/location/Location) 원문을 확인했다. `getSpeed()`는 위치 시점의 m/s이며 `hasSpeed()`가 참일 때 유효하다. Doppler 등을 사용하면 좌표 차분보다 정확할 수 있으나 모든 제공자/폰이 이를 보장하지 않는다. API 26 `getSpeedAccuracyMetersPerSecond()`는 `hasSpeedAccuracy()`가 참인 68% 신뢰 수준의 m/s 불확실성이다. 좌표 정확도와 별개다.

`elapsedRealtimeNanos`(API 17)를 시스템의 같은 monotonic 시계와 비교하여 수신 나이를 계산한다. `getElapsedRealtimeAgeMillis`는 API 33이라 min SDK 29에서는 기존 차분 방식을 유지한다. wall clock은 순서/속도 차분에 사용하지 않는다. [LocationRequest](https://developers.google.com/android/reference/com/google/android/gms/location/LocationRequest#getIntervalMillis())의 interval은 희망 간격이며 throttling 등으로 실제 위치는 더 느릴 수 있다. 엔진의 수신 나이 3초, 표시 만료 10초, 위치 사이 최대 15초를 하나의 값으로 설명하지 않는다.

## 재현·검증 계약

`ProviderPaceEngineTest`는 실제 RunEngine에 같은 좌표를 두 번 입력한다. 기준은 speedAccuracy 없는 기존 fallback, 후보는 명시적 품질 속도다. 직선·90도·180도·반경 2/5/20m 곡선에 500/1000/2000/4000ms 위치를 넣고, 매 관측의 전체 RunSummary와 모든 저장 지점이 동일한지 검사한다. 독립 기하의 이동거리·기준/후보 페이스 최대 오차를 CI 로그 `PROVIDER_PACE_COMPARE`로 출력한다. 이동 근거 8m가 부족한 조합은 표시 없음으로 유지하며 오차 0의 성공으로 해석하지 않는다.

불규칙 주기·실제 지속 감속, 속도 품질 결측/음수/비유한/큰 불확실성, 좌표 정확도 불량·장기 공백·표시 만료·수신 나이 초과, 정지 속도 튐과 수동 재개를 별도로 검사한다. [기존 고정 비교 자료](PACE_ESTIMATION_COMPARISON.md)의 baseline/CSV는 덮어쓰지 않으며 quality 미제공 fixture는 기존 fallback을 그대로 대조한다.

자동 검사는 [Android 워크플로](../.github/workflows/android.yml)의 JDK 25/JVM 21 환경에서 수행한다. 아래 내용은 재현 입력과 검사 범위를 설명하며, 커밋별 실행 결과는 [GitHub Actions](https://github.com/delvering17/runkeep/actions)에서 확인한다. 실제 야외 GPS·TTS·이어폰·배터리 검증은 자동 검사와 구분한다.

## 선택형 안정 코칭

기존 기본 정책은 20초/최소 8초·8m의 추정 창과 즉시 경보를 사용한다. 추가 2초/km 문턱과 경보 2초 지속은 사용하지 않는다. 이번에는 그 즉시 정책을 기본 `IMMEDIATE`로 그대로 둔다. `STABLE`은 사용자가 선택하는 별도 코칭 방식이다. 허용 범위 자체를 넓히는 숨은 문턱은 없다.

STABLE의 작은 이탈 진입/반전은 같은 방향의 새 GPS 관측 3개 이상과 첫 관측 이후 2초를 함께 확인한다. 500ms 위치에서는 2초를 채우는 데 5개가 필요하며, 1초 타이머나 같은 GPS 재평가는 관측 수를 늘리지 않는다. 반전 확인 중에는 이전의 반대 경보도 끄며, 경계 포함 정상 복귀는 즉시 무음이다. 절대 차이가 `max(30초/km, 허용오차×3)` 이상인 큰 이탈과 구간 목표 변경은 다음 평가에 즉시 반응한다. 이 수치는 옵션의 명시적 앱 정책이며, 최적 코칭값이나 실측 결과가 아니다. 음성의 10초 지속·실제 발화 시작 반복, 빠름/느림 음색과 메트로놈은 유지한다.

`StablePaceEngineTest`는 실제 엔진에 6:00/km 직선 거리와 결정적 0.6m 위치 잡음을 입력하고 기본/옵션의 표시 페이스와 모든 기록 필드가 같은지 비교한다. 같은 ±5초/km 평가에서 경보 시작/전환 횟수만 비교한다. 독립 직선 수식 분석은 30~240초에서 기본 경보 시작 112회를 예상하지만, 실제 JVM 엔진 결과는 `STABLE_PACE_COMPARE` CI 로그로 확인한다. 합성 잡음의 횟수를 야외 발생률로 해석하지 않는다. 10초 5:30→6:30 인터벌과 20초 5:00 이탈도 같은 입력으로 진입 시각을 출력하며 확인 지연이 최대 2초인지 검사한다. 20초 추정 창의 반응 지연과 옵션 확인 지연은 별개다.

## 독립 시간별 현재 안내

`periodicPaceVoice`는 기본 false, `periodicPaceSeconds`는 기본 30·정수 10~300초다. 범위는 앱 설계값이며 잘못 저장된 값은 30으로 정상화한다. voice가 상위 게이트이며 이탈 안내의 paceVoice와 상태/현재/목표 읽기 3개 선택에는 종속되지 않는다. 정상·목표 없음·계획 완료 후에도 RUNNING이고 유효 현재값이면 읽을 수 있다. 거리별 안내·1km 평균의 별도 옵션을 유지한다.

처음 유효한 현재값, 재개·GPS 복귀 또는 시간별 안내 켜기/간격 변경에서 현재 active time을 기준으로 한 주기 뒤에 안내한다. 정지·무효에는 기한을 버리고, 복귀 때 과거 횟수를 몰아 읽지 않는다. 타이머는 기한/신선도 평가만 하고 새 페이스를 만들지 않는다. 대기 CURRENT_PACE는 하나만 보관하고 수치는 발화 직전에 최신 값으로 갱신한다. 15초 수명·기존 큐 우선순위는 유지한다.

`PreparedRunSpeech`는 실제 요청할 event와 `RunSpeechToken`을 함께 반환한다. 서비스는 원래 큐 event를 선택하고 prepareSpeech 결과로 문장을 만든다. TTS 수락 시 원래 event만 acknowledge하고 speechRequested(token)을 호출한다. 서비스의 engine identity와 오디오 request identity 검사 후 실제 onStart에 speechStarted(token, now), 완료/오류/중지에는 speechCompleted(token)을 전달한다. 준비·실패·거절은 읽음 credit이 없다.

토큰에는 engine 소유권·세대·요청·문장에 실제 들어간 현재 수치를 담는다. onStart 당시 새 엔진 값을 이미 읽은 숫자로 간주하지 않는다. 실제 현재값을 읽은 onStart만 다음 주기를 재설정하고, 같이 대기한 시간별/거리별 현재 숫자가 실제 읽은 반올림 값과 같을 때 합친다. 이미 달라진 최신 숫자는 남긴다. 1km 평균과 이정표는 남긴다. 시간별 안내가 켜져 있고 같은 반올림 초/km를 실제 읽은 지 5초 이내라면 이탈 문장의 현재 숫자만 생략하고 상태/목표는 유지한다. 숫자가 달라졌다면 생략하지 않는다. 5초는 명시된 중복 처리 창이며 이탈 지속 조건이 아니다. 시간별 안내가 꺼진 기존 이탈 읽기 선택은 이 처리로 변경하지 않는다.

주기 안내와 1km가 겹치면 평균+현재를 한 문장으로 준비한다. 요청 후 실제 시작 전에 현재값이 무효가 되면 시작을 거부하고 completion에서 평균-only 1km를 재큐하여 이정표를 잃지 않는다. 발화 준비/대기는 옵션 3개·모드/허용오차·목표/방향·GPS·세대를 엄격히 확인한다. 실제 onStart 후에는 정상 복귀·방향/목표 변경·숫자/GPS 변화로 진행 문장을 자르지 않는 기존 음성 안내 계약을 보존한다. 옵션 또는 전체 음성 끄기·수동/자동 정지·종료·포커스 손실은 중지할 수 있다. 이미 시작한 1km 문장은 평균/현재 구절을 끝까지 보존하되, 무효/이전 세대 콜백은 새 안내의 읽음 credit을 갱신하지 않는다.

`PeriodicPaceEngineTest`는 정상/목표 없음, 8개 읽기 조합과 모두 끄기, 준비 실패/늦은 onStart/타 엔진 토큰, 설정 세대 변경, 최신 수치/실제로 읽은 숫자, GPS 무효·복귀·정지, 발화 시작 전/후 목표 전환, 시간별+거리별+1km 합침과 평균 복원을 실제 엔진 API로 검사한다. onStart 테스트는 합성 콜백이며 실제 한국어 TTS 시작/완료 시각을 측정한 결과가 아니다.
